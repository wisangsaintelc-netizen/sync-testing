BAPPS Sync — Guía técnica de implementación

Contrato de API, modelo de datos y estructura de código para el frontend y el backend

Documento complementario a la Documentación de diseño. Aquí está lo que el diseño no dice: cómo se comunican frontend y backend, qué endpoints existen, qué forma tiene cada request/response y cómo organizar el código. Principio rector: KISS. REST plano sobre JSON, sin GraphQL, sin websockets si un polling simple alcanza, sin abstracciones que nadie pidió. Cada decisión de aquí se puede borrar y reemplazar por algo más simple si no se está usando.

1. Principios KISS de integración

  • El backend envía datos crudos; el frontend decide cómo se ven. El backend nunca manda colores, ni labels traducidos de estado, ni HTML. Manda la clave de estado ("online", "failed"…) y el número/texto crudo. Todo lo visual (color de badge, formato de fecha relativa) lo resuelve el frontend con la tabla única. Esto evita duplicar la lógica de presentación en dos lados.
  • Un solo tipo de respuesta para listados. Todos los GET de lista devuelven la misma envoltura { data, page, total }. No hay respuestas "especiales" por vista. Aprender una, saber todas.
  • REST por recurso, verbos HTTP estándar. GET lee, POST crea/acciona, PATCH edita, DELETE borra. Nada de POST /getAgentsList.
  • Estados = enums cerrados. Los valores de status son un conjunto fijo (sección 4 del doc de diseño). El backend valida contra esa lista; si no coincide, es un bug del backend, no un caso a manejar en el frontend.
  • Polling antes que realtime. El dashboard y los datos "vivos" se refrescan con un GET cada N segundos. Solo se pasa a SSE/WebSocket si el volumen lo exige — y hoy no lo exige.

2. Convenciones de la API

TemaRegla
Base URL/api/v1 — versión en la ruta. Un cambio incompatible sube a /api/v2; el v1 sigue vivo hasta migrar.
FormatoJSON en request y response. Content-Type: application/json. Nombres de campo en snake_case.
AuthAuthorization: Bearer <token> en cada request. Login devuelve el token; el frontend lo guarda y lo adjunta. 401 → redirigir a login.
FechasEl backend siempre manda ISO 8601 UTC (2026-07-12T09:42:19Z). El frontend formatea a relativo ("hace 12 s") o local. El backend nunca manda "hace 12 s".
PaginaciónQuery params ?page=1&page_size=50. Respuesta incluye total para pintar el contador y el paginador.
FiltrosQuery params planos: ?status=failed&search=farmacia. El chip activo = un valor de status. El buscador = search.
Errores HTTPCódigos estándar: 400 datos inválidos, 401 sin auth, 403 sin permiso, 404 no existe, 409 conflicto, 422 validación, 500 error servidor. Cuerpo siempre { error: { code, message } }.
Zona horariaBackend en UTC. La app muestra hora del navegador o una zona fija del cliente (a definir por negocio, no por código).

Envoltura estándar de listado

GET /api/v1/agents?page=1&page_size=50&status=offline&search=farmacia

200 OK
{
  "data": [ /* array de objetos del recurso */ ],
  "page": 1,
  "page_size": 50,
  "total": 42
}

Forma estándar de error

422 Unprocessable Entity
{
  "error": {
    "code": "INVALID_CONFIG",
    "message": "interval_seconds debe ser >= 60, se recibió 15."
  }
}

El code es la misma familia de códigos técnicos que ya usa la app (sección 6). El message es el texto técnico; el mensaje "operativo" para soporte lo mapea el frontend por código.

4. Modelo de datos (payloads reales)

Estas son las formas exactas que hoy consume la UI. Los tipos y nombres provienen del código de la maqueta; el backend debe entregarlos tal cual (con status en las claves de la sección 5 y fechas en ISO — el ejemplo muestra los valores ya renderizados).

4.2 Ejecución (run) — GET /runs/{id}

{
  "id": "RUN-8842",
  "client": "Distribuidora El Sol",
  "agent": "AGT-000142",
  "sync": "clientes_valery",
  "status": "success",             // success|running|failed|skipped
  "trigger": "schedule",           // schedule|manual|command
  "started_at": "2026-07-12T09:42:11Z",
  "ended_at": "2026-07-12T09:42:19Z",   // null si running
  "rows_read": 1240,
  "rows_inserted": 900,
  "rows_updated": 340,
  "rows_failed": 0,
  "error": null,                   // código si failed/skipped
  "correlation_id": "corr-run-8842",
  "timeline": [ { "event": "run_started", "detail": "Trigger: schedule", "at": "..." } ]
}

El frontend calcula duration a partir de started_at/ended_at — el backend no la envía. El payload que muestra el drawer es un resumen derivado de estos mismos campos.

5. Enums — valores válidos (fuente de verdad compartida)

Backend y frontend comparten estas listas. Agregar un valor requiere tocar ambos lados y la tabla de estado del doc de diseño. Nada fuera de estas listas es válido.

CampoRecursoValores permitidos
statusagentonline · offline · enrolled · disabled
statusrunsuccess · running · failed · skipped
statuscommandpending · completed · failed · expired · skipped
status / enabledsyncenabled · disabled · paused
healthclientok · warning · error · enrolled
triggerrunschedule · manual · command
typecommandrun_now · pause_sync · resume_sync · refresh_config
kindauditcommand · event · error · config · auth

Regla de resolución del frontend: meta(status) devuelve {label, bg, fg, dot}; un valor desconocido cae a "Deshabilitado" gris. Por eso un enum mal escrito por el backend se ve gris, no rompe la UI — pero es un bug a corregir.

6. Códigos de error del dominio

El backend usa estos códigos en last_error, run.error y error.code. El frontend mapea cada código a su mensaje operativo, mensaje técnico y acción sugerida — el backend puede omitir esos textos y dejar que la UI los provea, o enviarlos si varían por caso.

CódigoReintentableSignificado (operativo)
SOURCE_CONNECTION_FAILEDSíNo se pudo conectar al sistema administrativo del cliente
CENTRAL_API_UNAVAILABLESíEl centro BAPPS no respondió al enviar el lote
SYNC_ALREADY_RUNNINGSíSe intentó ejecutar un sync que ya estaba corriendo (→ skipped)
SCHEMA_CHANGEDNoLa estructura de la tabla origen cambió
AUTHENTICATION_FAILEDNoCredenciales del agente rechazadas por el centro
INVALID_CONFIGNoLa configuración del sync tiene un valor inválido

retryable es un dato del backend por código: gobierna si el botón "Reintentar" está activo. No lo infiere el frontend.

7. Datos vivos: polling (KISS) antes que realtime

DatoFrecuencia sugeridaCómo
Métricas del dashboardcada 15 sGET /dashboard/metrics en un intervalo; reemplaza el estado
Ejecuciones "running"cada 10 s mientras haya alguna running visibleRe-fetch de GET /runs; parar el intervalo si ninguna está running
Heartbeat de agentesal abrir la vista + botón refrescar manualEl botón de refresco de la topbar dispara el re-fetch (ícono gira 0.9 s)
Estado de un comando enviadocada 5 s hasta completed/failed/expiredPoll corto de GET /agents/{code} tras enviar el comando

Regla KISS: empezar solo con el botón de refresco manual. Agregar polling automático vista por vista cuando se sienta la falta. Migrar a SSE/WebSocket solo si el polling genera carga real medida — no de forma preventiva.

8. Estados de UI que el backend condiciona

El diseño documenta estados de dato; el frontend además debe cubrir estados de red. Cada listado y drawer tiene cuatro:

EstadoCuándoQué muestra
CargandoPetición en cursoSkeleton de filas/tarjetas con la misma geometría (no spinner a pantalla completa)
Vacíodata: [] con 200 OKMensaje neutro centrado ("Sin agentes que coincidan"), sin color de error
Error de red4xx/5xx o fallo de fetchAviso rojo con el message del error + botón "Reintentar"
Sin permiso403Ocultar la acción/vista; no mostrar datos que el rol no puede ver

9. Estructura de código sugerida (frontend)

Estructura mínima que refleja 1:1 la arquitectura de vistas del diseño. Sin capas extra "por si acaso".

src/
  api/
    client.js         // fetch con baseURL + bearer; envoltura de listados
    endpoints.js      // una función por endpoint de la sección 3
  lib/
    status.js         // meta(status) → {label,bg,fg,dot}  (tabla única)
    format.js         // fecha ISO → relativa, duración, números
    errors.js         // código → {opMsg, action, retryable}
  components/
    StatusBadge, Table, FilterBar, Chip, Drawer, Card, Button, Notice
  views/
    Dashboard, Agents, Assign, Runs, Audit, Clients, Catalog
  layout/
    Sidebar, Topbar

Tres archivos son el corazón del contrato: status.js (única fuente de color por estado), format.js (todo formateo de fecha/número vive aquí, no en las vistas) y errors.js (mapa código→texto). Si un color de estado o un formato de fecha aparece escrito a mano dentro de una vista, es una violación del patrón — debe salir de estos tres archivos.
